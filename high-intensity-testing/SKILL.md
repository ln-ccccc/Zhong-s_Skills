# 超高强度审查与测试(high-intensity-testing)

三轮实战全面审查(2026-09-14 / 09-16 / 09-19,累计 60+ 发现全数闭环,其中一轮 32 发现 = 29 修 / 1 接受 / 1 证伪 / 2 悬置)沉淀的完整方法论。**用途**:对一个大分支、一批修复或整个系统做"作者查不出自己 bug"级别的对抗性审查与测试。

## 一、三源融合

| 来源 | 贡献 | 层次 |
|---|---|---|
| [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) | 五个工程 skill:规划拆解 / TDD / 增量实现 / git 工作流 / 调试纠错 | 纪律层 |
| [alibaba/open-code-review](https://github.com/alibaba/open-code-review)(OCR CLI) | 免 LLM key 的规则化审查驱动(委托模式):文件选择 + 规则解析 | 工具层 |
| 自研测试方法论(六步工作法 + 失效模式技巧库 T2–T30) | 教训转定向检查指令 + 失效机制驱动的测试设计 | 执行层 |

**核心命题**(为什么需要这个 skill):写码模式的成功标准是"测试绿",作者盲区因此系统性漏检;单上下文长会话的注意力稀释让审查后半程失焦;项目契约知识不转化为检查清单,就永远测不出契约局部违反。对策 = **写码与审查分离 + 分治 + 教训转定向指令 + 审查发现固化成测试**。

## 二、全流程五阶段

```
规划(拆任务) → OCR 起手(选文件+出规则) → 并行审查(六步工作法)
     → 修复(TDD+增量+Stop-the-Line) → 验收门(权威环境+声明对照+固化测试)
```

每个阶段独立可验证;审查与修复**必须分离**(至少换对话 + 明确"无改动包袱的审查者"角色),不允许同一上下文既写码又自审。

## 三、阶段一:规划纪律(agent-skills 落地)

| skill | 落地纪律 |
|---|---|
| `planning-and-task-breakdown` | 全部工作分解为独立可验证任务(XS ≤10 行 / S ≤50 行 / M ≤150 行,均含测试);每任务 ≤3 条验收标准 + 明确验证命令 + 依赖关系;每阶段一个检查点 |
| `test-driven-development` | 每个缺陷修复先立复现测试(**Prove-It:先红后绿**——回归测试必须在未修复的代码上先跑红,否则没有证明力) |
| `incremental-implementation` | 一任务一垂直切片,独立可验证、独立可回滚,禁止跨任务攒批 |
| `git-workflow-and-versioning` | 原子提交(conventional commits),**每 commit 立即 push**,不攒批;提交信息注明影响面与"未触碰"范围 |
| `debugging-and-error-recovery` | **Stop-the-Line 制度化**:测试网为红时禁止任何新提交;修复必须含"防回潮"测试 |

## 四、阶段二:OCR 工具层起手

审查/测试任务**以 `ocr delegate` 起手**,由它做文件选择与规则解析,agent 自身模型执行评审:

```bash
npm install -g @alibaba-group/open-code-review   # 命令 ocr,依赖 Git ≥ 2.41

ocr delegate preview                              # 预览选中文件与规则组(免 LLM key)
ocr delegate rule <files...>                      # 按规则执行评审
ocr review                                        # 工作区变更
ocr review --from main --to <branch>              # 区间审查(修复分支验收常用)
ocr review --commit <sha>                         # 单提交
ocr scan --path <dir>                             # 无 git 历史的全量扫描
ocr review --resume <session-id>                  # 恢复中断会话
ocr ... --format json --output result.json        # agent 消费:逐条映射到报告模板
```

工作区干净时 `delegate preview` 输出 0 reviewable 属健康。OCR 输出的规则组**注入子代理任务书**使用,不是替代六步工作法。

## 五、阶段三:六步审查工作法(核心)

1. **分治**:按模块拆 3–4 个并行子代理(如 backend / frontend / 服务层 / 基础设施),各自独立上下文 + 详细任务书,**互不知晓彼此结论**(避免锚定)。
2. **地雷图注入**:任务书必含两类内容——①项目契约(接口约定、数据顺序、生命周期、白名单等硬约束);②历史教训清单。把教训转成定向检查指令:**"已知模式 X,找同类未修实例"是最高产的手法**(实战中第三处同类断线即由此抓到)。
3. **契约驱动 + 跨层对照**:前后端字段名 / payload / 键名 grep 对照;逐入口核对契约;跨层数据流走完整链路(生产者→消费者两侧都走到)。
4. **git 考古**:`git log -S` 找功能死亡提交;diff 对照旧语义;功能"消失"往往有明确提交可考。
5. **抽查验证**:子代理报告的每条 P0/P1,主控**亲自到代码确认(file:line 复现)后才采信**——压制幻觉;两个独立代理交叉命中同一问题可视为免复验信号。
6. **固化成契约测试**:审查发现全部落成测试(键集对齐 / 接线断言 / 超时存在 / 状态码回归),让下一轮审查清单变短。

### 修复验收专用:声明 vs 实现逐条对照(T26)

对上一轮**每条修复声明**给出实现证据(file:line)或判定不成立——修复提交声称的行为与代码实际行为不符(收口漏改 / 透传死键 / 守卫失效)是修复批次最高发的缝隙,实战中一轮 4 个 P1 有 3 个由此捕获。配套警惕:**死键裁决前必须按名字全仓 grep**(T29,变量是按名字被读的,只 grep 旧消费者文件名会漏掉新消费者)。

## 六、阶段四:修复纪律

- **并行修复模式**(大批判定流程):并行子代理 + 文件所有权互斥 + 冻结跨代理契约 + worktree 分支隔离 + 主控逐 diff 验收 + 合并后全量门。实战记录:4 分支零冲突、全部门全绿。
- 每个 commit 立即 push;测试网红时冻结一切新提交(Stop-the-Line)。
- 每个修复附带回归墓碑(T12):先在旧代码上跑红,修复后变绿。

## 七、阶段五:失效模式技巧库

### 7.1 十五问触发清单(没有测试思路时逐条自问)

| # | 自问 | 对应技巧 |
|---|---|---|
| 1 | 同一操作**连续跑第二遍**会怎样? | T3 连续运行验证 |
| 2 | 换一批**形态不同**的输入(格式/规模/来源)会怎样? | T4 混合批次抽样 |
| 3 | 输入为空 / 极大 / 非法 / 重复会怎样? | T6 边界值与等价类 |
| 4 | 用**真实业务数据**(而非手工造的数据)跑会怎样? | T7 数据真实性 |
| 5 | 客户端**中途断开 / 超时 / 取消**会怎样? | T8 异常路径 |
| 6 | 依赖的服务**不可用**时,是明确报错还是静默出错? | T8 异常路径 |
| 7 | **两个相同请求同时到达**会怎样? | T9 并发与竞态 |
| 8 | 连续运行一整夜,内存/句柄/磁盘会缓慢泄漏吗? | T10 浸泡测试 |
| 9 | 把依赖进程 **kill -9** 会怎样?能自愈吗? | T11 故障注入 |
| 10 | 这次修复**留下回归测试**了吗? | T12 回归墓碑 |
| 11 | 我是在**真实部署环境**里测的吗? | T13/T19/T22 环境一致性 |
| 12 | 性能优化前,有**分阶段基线数据**吗? | T14 先测量后优化 |
| 13 | 测试过程会把密码/密钥写进日志、截图或临时文件吗? | T15 敏感信息 |
| 14 | 自动化测试失败时,分得清**产品缺陷还是工具限制**吗? | T16 工具限制隔离 |
| 15 | 页面内容超过一屏时**能滚动吗**?滚到底内容完整吗? | T17 满屏滚动验证 |

### 7.2 技巧速查(T2–T30)

每条 = 失效一句话 + 关键动作一句话。编号沿用源 playbook(其中 T4 仅在触发清单引用,T5 未使用);每条的"为什么有效"论证与实战实证案例见源文档 `docs/testing_playbook.md`。

**策略层**

| ID | 技巧 | 失效 | 关键动作 |
|---|---|---|---|
| T2 | 递进验证 | 单次通过≠批量可用 | 冒烟→小批次(≥3 组,必含上次失败过的输入)→全量,逐级放大 |
| T3 | 连续运行验证 | 状态残留只在第二次暴露 | 修复类改动同输入连跑两遍,第二遍标准与第一遍一致 |
| T4 | 混合批次抽样 | 手工造数太规整 | 混合格式/规模/来源的输入分组抽测 |
| T10 | 浸泡测试 | 泄漏短时数学上不可见 | 长时连续运行,盯内存/句柄/磁盘曲线 |
| T11 | 故障注入 | 容错代码只在真故障时执行 | kill -9 依赖进程/断网/磁盘满,验**恢复能力**而非"没崩" |

**用例设计层**

| ID | 技巧 | 失效 | 关键动作 |
|---|---|---|---|
| T6 | 等价类+边界值 | 缺陷在边界聚集 | 每个数值参数取:最小、最小+1、正常、最大-1、最大、越界 |
| T7 | 数据真实性 | 隐含假设不体现在造数里 | 测试数据从权威资产生成,格式分叉每类至少一条真实样本 |
| T8 | 异常路径 | 异常分支双重覆盖不足 | 每个外部交互至少三条负面用例:空输入、错误凭证、中断 |
| T9 | 并发与竞态 | 时序交错串行碰不到 | 先验证"有无锁/队列"结构事实,再决定是否压测 |

**工程与工具层**

| ID | 技巧 | 失效 | 关键动作 |
|---|---|---|---|
| T12 | 回归墓碑 | 修过的 bug 复活是静默的 | 回归测试先在未修复代码上跑红,否则无证明力 |
| T13/T19/T22 | 环境一致性 | 测试结论在错误环境失效 | 解释器钉死到与生产一致;py_compile 也一样;权威门=重建后镜像容器内全套重跑,宿主只算冒烟 |
| T14 | 先测量后优化 | 性能直觉系统性失准 | 先加分阶段计时拿分布(中位数抗离群),再决定优化对象 |
| T15 | 敏感信息管理 | 日志/截图/临时文件是遗忘泄露面 | 画凭证值流向图,每个落点要么不持久、要么即用即删、断言只出布尔 |
| T16 | 工具限制隔离 | 把工具问题当 bug 修(或反之) | 替代路径验证(坐标点击/人工操作)后再下结论,结论必须带证据 |
| T17 | 满屏滚动验证 | 全局 overflow:hidden 静默裁剪 | 每页实测"滚到底+滚回顶",窗口调小复测,检查底部内容可交互 |
| T18 | 渲染取证 | 截图后端失真误导判断 | 截图异常先 DOM 取证:元素计数、path d 长度、elementFromPoint、canvas 解码像素 |
| T20 | 悬浮层遮挡裁剪 | 窄容器+长类目名冲突 | 逐条目悬停,断言 tooltip ⊆ 宿主容器 ∧ ⊆ 视口;根治优先于悬停补偿 |
| T21 | 自动化直达 vs 用户路径 | 底层 API 短路了入口链路 | 涉及入口控件的用例一律从真实入口驱动(点按钮/filechooser),底层注入只做预置 |
| T23 | 共享临时目录清理契约 | 后到者 rmtree 吞掉先到者产物 | 写入方用独立 mkdtemp;契约测试断言"产物不在共享目录内" |
| T24 | 验证链依赖被修 bug | 修复后验证基建反向断裂 | healthcheck 用语义化端点;修状态码/语义类 bug 后 grep 全部消费方 |
| T25 | junction 穿透删除 | 递归删除沿链接删空目标 | 摘链接用 `cmd /c rmdir`,枚举用 ReparsePoint;跨 shell 拼命令先只读枚举确认 |
| T26 | 修复声明 vs 实现对照 | 声称的行为无实现或无测试锁 | 每条修复声明要 file:line 证据;双代理独立命中可免复验 |
| T27 | 语法守卫目标解释器实测 | 守卫从未被喂过非法样本(假绿) | 守卫=子进程目标解释器+元测试自证+缺解释器显式 skip 告警 |
| T28 | autocrlf 检出漂移 | 同 blob 不同磁盘字节→门分裂 | 先比两个检出的 md5 再下结论;行尾判定用 `file`/`od -c` 交叉验证 |
| T29 | 死键裁决 grep 键名 | 只 grep 旧消费者文件名漏新读者 | 名字级全仓 grep + 枚举 `process.env.`/`getenv` + 查契约测试锁定 |
| T30 | 验证车辆复刻运行形态 | 车辆失配→契约正确拒绝→假红 | 跑门前核对车辆清单(GPU/设备变量/种子卷/挂载 vs 烘焙);重复性失败优先怀疑车辆 |

## 八、验收与报告标准

- **证据**:每条发现带 `file:line`,宁缺毋滥——存疑的不写,写了的都能复现。
- **分级**:P0(阻断/数据损毁)/ P1(功能破损/契约违反)/ P2(P3),每条给修复建议。
- **闭环**:发现 → 修复计划(拆任务) → 修复(TDD) → T26 声明对照 → 固化成测试 → 权威环境全量门。六环缺一不可。
- **权威门**:所有测试在钉死解释器的权威环境跑(容器/CI),宿主只作冒烟;门红即 Stop-the-Line。

## 九、超高强度模式执行单(照做即可)

1. 换新上下文,明确"无改动包袱的审查者"角色,禁止顺手改码。
2. `ocr delegate preview` 起手,拿到文件选择 + 规则组。
3. 按模块拆 3–4 个并行子代理;任务书 = 项目契约 + 历史教训地雷图 + OCR 规则组;子代理互不知晓。
4. 主控对每条 P0/P1 亲自 file:line 复现后才采信。
5. 报告定稿(分级 + 证据 + 修复建议,宁缺毋滥)。
6. 修复按 agent-skills 拆任务(XS/S/M + ≤3 验收标准 + 验证命令写死权威跑法);每修复先立 Prove-It 复现测试(先红后绿)。
7. 修复完成后跑 T26 逐条声明对照 + T29 死键复查。
8. 全部发现固化成契约测试/回归墓碑。
9. 权威环境全量门通过(解释器钉死、镜像内、车辆形态匹配),期间任何红即冻结提交。
10. 每 commit 立即 push,不攒批。

## 边界(何时不用)

- 单文件小改动、纯样式调整:直接自测,不需要分治与 OCR 起手。
- 无持久状态、无外部交互的纯函数:单元层重复执行即可替代递进验证(T2 何时可省条款)。
- 时间盒极紧的 hotfix:至少保住"Prove-It 先红后绿 + 权威门"两环,其余可裁剪,但要在提交信息里注明裁剪了什么。
