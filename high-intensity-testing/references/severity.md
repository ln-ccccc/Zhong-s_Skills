# 严重度定义与证据契约

## 分级定义

| 级别 | 名称 | 判定 | 准入门槛 |
|---|---|---|---|
| P0 | Blocker | 数据损毁、安全漏洞、主链路不可用 | **可执行复现**(file:line + 复现步骤/命令),复现失败即撤条 |
| P1 | Major | 功能破损、契约违反、静默产出错误结果 | **可执行复现**,同上 |
| P2 | Moderate | 边界缺陷、防御缺失、可维护性问题 | 代码级证据(file:line + 机制说明) |
| P3 | Minor | 文案、样式、日志质量 | 描述性证据即可 |

## 核心原则:P0/P1 = evidence,不是 consensus

**双代理交叉命中只提升置信度与优先级,不替代可执行复现。**

理由:两个代理并不统计独立——同模型家族、同仓库、同 diff、同提示模式、同底层先验,

```
same model family + same repository + same diff + same prompt pattern
        ↓
correlated hallucination(相关幻觉)
```

两个代理同时错完全可能。因此:

- 交叉命中 → finding confidence / priority ↑
- P0/P1 → 仍必须 executable reproduction,主控亲自复现后才可写入报告
- 主控复现失败 → 该条降级为线索或直接丢弃,报告宁缺毋滥
- 主控复现成功但定级不当 → 以主控实测调整级别

## 修复验收的对照纪律(T26)

对上一轮**每条修复声明**给出实现证据(file:line)或判定"声明不成立"——声称的行为与实际行为不符(收口漏改、透传死键、守卫失效)是修复批次最高发的缝隙。配套 T29:宣布任何配置键/环境变量已死前,必须按**名字**全仓反查(消费者按名字读取,不按旧消费者文件名)。
