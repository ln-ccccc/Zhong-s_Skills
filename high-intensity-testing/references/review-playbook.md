# 审查与修复全流程手册(五阶段)

```
规划(按风险拆任务) → 预检(OCR 或降级) → 并行审查(六步工作法)
     → 修复(TDD+增量+Stop-the-Line) → 验收门(权威环境+声明对照+固化测试)
```

每个阶段独立可验证。审查与修复**必须分离**(至少换对话 + 明确"无改动包袱的审查者"角色)。

## 一、规划纪律

| 纪律 | 要求 |
|---|---|
| 任务拆解 | 全部工作分解为独立可验证任务;**尺寸按风险定**:`Risk = contract_surface × statefulness × external_dependencies × rollback_cost`(契约面 × 有状态性 × 外部依赖 × 回滚代价),行数只作辅助参考——3 行动到鉴权逻辑也可能是大任务。每任务 ≤3 条验收标准 + 明确验证命令 + 依赖关系;每阶段一个检查点 |
| 测试驱动(TDD) | 每个缺陷修复先立复现测试(**Prove-It:先红后绿**——回归测试必须在未修复的代码上先跑红,否则没有证明力) |
| 增量实现 | 一任务一垂直切片,独立可验证、独立可回滚,禁止跨任务攒批 |
| 版本控制 | 原子提交(conventional commits)。**commit 本地随时可打;push 到远端仅在获得明确授权时执行;受保护分支未经显式许可永不推**——push 是外部副作用,权限级别高于本地写测试 |
| 调试纠错 | **Stop-the-Line 制度化**:验证门为红时禁止任何新提交;修复必须含"防回潮"测试 |

## 二、预检:OCR 可用则委托,不可用则降级

```
ocr CLI 可用?
   ├─ yes → ocr delegate preview          # 预览选中文件与规则组(免 LLM key)
   │        ocr delegate rule <files...>  # 按规则执行评审
   └─ no  → 降级路径:
            git diff --name-only / git status --porcelain   # 变更面
            git diff main...HEAD --stat                     # 分支范围
            读 AGENTS.md / CLAUDE.md / .cursorrules 等仓库规则文件当规则源
```

常规命令(OCR 可用时):`ocr review`(工作区)/ `ocr review --from main --to <branch>`(区间)/ `ocr review --commit <sha>`(单提交)/ `ocr scan --path <dir>`(全量)/ `--resume <session-id>`(恢复);agent 消费加 `--format json --output result.json`。

预检可直接跑 `scripts/review-preflight.py [repo_dir]`,自动探测并输出 JSON(files / rule_files / mode)。规则组(无论来源)**注入子代理任务书**使用,不替代六步工作法。

## 三、六步审查工作法(核心)

1. **分治**:按模块拆 3–4 个并行子代理,各自独立上下文 + 详细任务书,**互不知晓彼此结论**(避免锚定)。
2. **地雷图注入**:任务书必含两类内容——①项目契约(接口约定、数据顺序、生命周期、白名单等硬约束);②历史教训清单。把教训转成定向检查指令:**"已知模式 X,找同类未修实例"是最高产的手法**。
3. **契约驱动 + 跨层对照**:接口字段名 / payload / 键名 grep 对照;逐入口核对契约;跨层数据流走完整链路(生产者→消费者两侧都走到)。
4. **git 考古**:`git log -S` 找功能死亡提交;diff 对照旧语义;功能"消失"往往有明确提交可考。
5. **抽查验证**:子代理报告的每条 P0/P1,主控**亲自到代码确认(file:line 复现)后才采信**。双代理交叉命中只提升置信度与优先级,**不替代复现**——两个代理不统计独立(同模型、同仓库、同 diff、同提示模式),相关幻觉完全可能同时发生。P0/P1 = evidence,不是 consensus(详见 severity.md)。
6. **固化成契约测试**:审查发现全部落成测试(键集对齐 / 接线断言 / 超时存在 / 状态码回归),让下一轮审查清单变短。

## 四、修复纪律

- **并行修复模式**(大批判定流程):并行子代理 + 文件所有权互斥 + 冻结跨代理契约 + 分支/worktree 隔离 + 主控逐 diff 验收 + 合并后全量门。
- 修复完成后跑 **T26 修复声明 vs 实现逐条对照**:对每条修复声明给出实现证据(file:line)或判定不成立;配套 **T29 死键复查**(判死必须按名字全仓 grep)。
- 每个修复附带回归墓碑(T12):先在旧代码上跑红,修复后变绿。
- 门红即冻结一切新提交(Stop-the-Line)。

## 五、验收门

- 所有测试在**钉死解释器的权威环境**跑(与生产一致的容器/CI),本机只作冒烟。
- 跑门前核对车辆清单(T30);重复性失败优先怀疑车辆,单次性失败优先怀疑代码。
- 全量门通过 + T26 对照清零 + 回归墓碑全绿,才算闭环。

## 六、超高强度模式执行单(照做即可)

1. 换新上下文,明确"无改动包袱的审查者"角色,禁止顺手改码。
2. 预检起手:跑 `scripts/review-preflight.py`(OCR 可用走委托,不可用走 git/规则文件降级),拿到文件面 + 规则组。
3. 按模块拆 3–4 个并行子代理;任务书 = 项目契约 + 历史教训地雷图 + 预检规则组;子代理互不知晓。
4. 主控对每条 P0/P1 亲自 file:line 复现后才采信;复现不了的丢弃。
5. 报告定稿(按 report-template.md:分级 + 证据 + 复现步骤 + 修复建议,宁缺毋滥)。
6. 修复按规划纪律拆任务(风险尺寸 + ≤3 验收标准 + 验证命令写死权威跑法);每修复先立 Prove-It 复现测试(先红后绿)。
7. 修复完成后跑 T26 逐条声明对照 + T29 死键复查。
8. 全部发现固化成契约测试/回归墓碑。
9. 权威环境全量门通过(解释器钉死、与生产一致的运行环境、车辆形态匹配),期间任何红即冻结提交。
10. commit 本地原子化;**push 仅在授权范围内执行,受保护分支不推**。

## 七、边界(何时不用)

- 单文件小改动、纯样式调整:直接自测,不需要分治与预检。
- 无持久状态、无外部交互的纯函数:单元层重复执行即可替代递进验证(T2)。
- 紧时间 hotfix:至少保住"Prove-It 先红后绿 + 权威门"两环,裁剪项写进提交信息。
